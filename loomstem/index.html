🎉 That's a real rollercoaster, built by you.

    
Here's the honest part most demos skip: your blocks only ever called one thing — trackPoint(height). That's a real, pre-built LoomSTEM action, the same way forward() is in the Art world. It's not LoomScript you wrote yourself; it's a tool the language gives you, and behind it, this exact formula runs every single time it's called:

    
new speed² = old speed² + 2 × gravity × (old height − new height)

    
Not a simplified version, the real one — it's why the very first drop and every drop after it can genuinely produce different numbers depending on how fast the cart already was, exactly like conservation of energy actually works. trackPoint() hides the arithmetic the same way a calculator hides how it does long division — it's still really happening, just inside a tool built to do it for you.

    
Same blocks. Same compiler. The only thing you changed was one number — real physics decided the rest, live, the same way it will for a student building their own ride, their own bowling game, or their own chemistry experiment.

    
One more thing worth noticing: every script you just built started with @engine: physics. That's a genuine declaration, not decoration — it tells the compiler which part of the language this program is allowed to use. Try the sandbox's engine dropdown with something other than "physics" and press Run: it won't silently do nothing, it'll tell you exactly why trackPoint() doesn't belong there. This is a prototype — most LoomSTEM programs don't have this line yet — but it's how a real, deliberately-declared engine boundary would work.

That's the actual point of a loop: do the repeating part once, let it run itself.


    

      

        
Without a loop (the warm-up)

One more block, every time, for every extra point

      

      
→

      

        
With a loop (just now)

        
repeat 5 times {
  trackPoint(height)
  height = height - 15
}

        
Same 5 points — and just as easily 50

      

    


    

      🔑 The trick: height changes inside the loop, so all 5 runs use a different number — automatically, not because you typed 5 different blocks.
    


    

      Want the physics and engine details? ▾
      
Every point still runs the exact same real formula as before — trackPoint() calls new speed² = old speed² + 2 × gravity × (old height − new height) each time the loop calls it, five times over. The loop changes how many times it runs and with what numbers; it never changes what the formula does.

      
The climb you tested in the playground is the same rule, spent differently: the loop's drop earns speed, the climb spends it, and asking for more climb than the drop earned genuinely fails — not a rule, just the arithmetic not allowing it.

      
Every script here also started with @engine: physics — a real, checked declaration. Pick a different engine in the sandbox and press Run to see it caught, not ignored.

🎉 That's a real, playable adventure — with a real memory.

    
Here's the part that's actually clever: the story remembered whether you picked up the torch, minutes of "story time" earlier, and used that to decide which choice you were even allowed to see later. That's not a script pretending to branch — it's a genuine condition, checked live, every time.

    
+ [Switch on the torch] -> sawEverything {item: torch}

  ...is read as: "only offer this choice if the player is
  carrying a torch." The mirror-image choice checks {!item: torch} --
  exactly one of the two can ever be true at once.

    
Everything else — the -> target arrows, the node headers — works exactly like it did before. Conditions are just one more real ingredient, not a different system. That's how a two-choice story and a fifty-node story with inventory, flags, and branching consequences are built the same way, just with more of it.

    
You'll also have noticed every script started with @engine: if — the same declaration line LoomSTEM's coding side uses. Worth being honest about the difference: in LoomSTEM, that line is actively checked — call a physics action under a chemistry declaration and it's caught. Here, it's currently a declared header only; Loom doesn't dispatch across multiple engines the way LoomScript calls out to physics or chemistry, so there's no mismatch to catch yet. Same line, same intent, not yet the same enforcement — that gap is real, not glossed over.
